## 一、总体结论（先行）

这是一个**工程成熟度明显高于一般个人项目**的代码库：有 spec 驱动的变更流程（openspec）、事故复盘文档、TLA+ 形式化验证、对 WinFsp 官方 memfs 的 1:1 差分测试、针对最坏缓存配置的回归夹具。热路径设计（同步 ValueTask、锁外预分配页、稀疏页表、归还即清零）也经得起推敲。

但存在 **4 个经实测确认或静态确认的 P0 级缺陷**，集中在三个主题：

1. **容量记账体系有漏洞**——`PagePool.Rent()` 从空闲栈弹页时不检查预留（reservation），导致 `SetLength` 预留的容量可被其他文件偷走，承诺超卖、`FreeBytes` 可为负、被预留方在磁盘"未满"时收到 DISK_FULL。**【实测复现】** 预留后仅剩 64KB 空闲时，另一文件仍成功写入 63.9MB；空闲空间显示为 `18446744073701163008`（负值 −8,388,608 的 ulong 回绕）；随后预留方自己写入 1 页即报"磁盘空间不足"。这与 README 宣称的 TLA+ 验证性质（`FreeBytesAccurate`、`PoolConsistent`）矛盾，说明模型未覆盖"空闲栈复用 × 预留"的交互。
2. **目录可被移动进自身子树（大小写绕过）**——常规重命名会被 Win32 层拦下，但仅大小写不同的目标路径（`a` → `A\inner\newa`）可绕过该检查直达文件系统，产生自引用环：目录树变成 `a\inner\newa\inner\newa\…` 无限自嵌套。**【实测复现】** 后果：任何长路径递归遍历工具会无限循环，卸载时的 `Dispose` 递归会撞环；常规资源管理器/`rd` 无法清理（我在实测后需先重命名断环才能删除）。
3. **失败路径的顺序问题**——`OverwriteFile` 先截断再检查容量，DiskFull 时原数据已被摧毁。（此条无法从用户态简单触发，仍为静态结论。）

**实测中同时澄清了一项误报**：删除语义（显式删除、delete-on-close、Move-replace 三条路径在仍有句柄打开时）均表现正确，与 NTFS 一致——原报告 P0-4 降级为设计建议，详见 §三 与 §八。

另发现一项**部署配置问题**：该机的 `HKLM\SOFTWARE\WOW6432Node\WinFsp\MountUseMountmgrFromFSD` 未设置，R 盘走 DefineDosDevice 回退路径挂载——`Get-Volume`/存储 WMI 均不可见该卷（实测确认），基准工具与部分应用看不到这个盘。以管理员身份运行一次 `Setup.bat` 或安装器可修复。

## 三、问题清单（按严重度）

> 定位均相对于 `src/` 下的源码文件。严重度定义：**P0** 数据丢失/结构损坏/记账错误；**P1** 与 NTFS 语义或自有 oracle 分歧、可导致应用错误；**P2** 健壮性/边界/卫生；**P3** 风格与长期维护。

### P0-1 预留容量可被 `Rent()` 偷走：承诺超卖、`FreeBytes` 可为负【实测复现】

**位置**：`RamDrive.Core/Memory/PagePool.cs:59-100`（`Reserve` / `Rent`）、`:171-190`（`AllocateNewPageIfUnderCapacity`）

**事实**：`Reserve()` 维护不变式 `rented + reserved ≤ maxPages`；新页分配路径 `AllocateNewPageIfUnderCapacity` 也检查 `allocated + reserved ≥ maxPages` 才拒绝。**但 `Rent()` 从 `_freePages` 空闲栈弹页的快路径没有任何预留检查**：

```csharp
if (_freePages.TryPop(out nint page))   // ← 不看 _reservedCount
{
    Interlocked.Increment(ref _rentedCount);
    return page;
}
```

**推演（确定性复现序列，非并发竞态）**：容量 10 页。
1. 文件 A `SetLength` 扩展 → `Reserve(10)` 成功（rented=0, reserved=10）。
2. 文件 B 写 1 页 → 空闲栈非空（此前有过分配-归还，或 `PreAllocate=true`）→ `Rent()` 直接弹走 1 页 → rented=1。
3. 此时 committed = 11 > maxPages = 10。`UsedBytes = (rented+reserved)×pageSize` 超过容量，**`FreeBytes` 为负**，经 `GetVolumeInfo` 的 `(ulong)` 转换后资源管理器会看到约 16EB 的"可用空间"。
4. 文件 A 随后写入：`RentBatch` 只能拿到剩余的 9 页，`AllocateNewPageIfUnderCapacity` 因 `allocated + reserved ≥ max` 拒绝 → **预留方反而收到 DISK_FULL / 部分写**。

**影响**：`PreAllocate=true` 时空闲栈恒非空，必现；默认按需模式下只要池里有过回收页即可触发。这直接违反 README 宣称的 `PoolConsistent` / `FreeBytesAccurate` TLA+ 性质——模型大概率未建模"空闲栈复用与预留共存"。

**实测记录（2026-09-04，真实挂载的 R 盘，2048MB/64KB 页）**：
- 变体 1：文件 A `SetLength` 预留至仅剩 64,536 字节空闲 → 另一文件 WriteThrough 写入 129 页**全部成功** → `Get-PSDrive R` 显示空闲 = **18,446,744,073,701,163,008**，恰为 −8,388,608（−128 页）的 `ulong` 回绕值，与静态推演逐位吻合。
- 变体 2（端到端）：预留至仅剩 64KB → 第二个文件持续写入，在写下 **1,022 页（63.9MB）** 后才收到"磁盘空间不足"→ 随后**预留方自己写入 1 页同样报"磁盘空间不足"**。即：一个声称只剩 64KB 的盘接受了近 64MB 写入，而提前预留了 2,047.9MB 的文件却拿不到 64KB。
- 清理后 `used + free` 精确恢复为 2,147,483,648（容量守恒），未观察到页泄漏。

**修复建议**：把 `rented` 与 `reserved` 合并为单一原子承诺计数 `committed`，所有消耗容量的路径（空闲栈弹页、新分配、预留）统一走 `CAS(committed + n ≤ maxPages)`；归还/取消预留时回退。`FreeBytes = (maxPages − committed) × pageSize`。同时在 Debug 构建加断言 `committed ≤ maxPages` 与 `_reservedCount ≥ 0`。修复后**更新 `tla/RamDiskSystem.tla` 使空闲栈复用与预留共存**，补一条 `PreAllocate=true` 的集成测试。

### P0-2 `OverwriteFile` 先截断后检查容量：DiskFull 时数据已被摧毁

**位置**：`RamDrive.Core/FileSystem/WinFspRamAdapter.cs:293-322`

**事实**：

```csharp
long sizeBefore = node.Content.Length;
node.Content.SetLength(0);                       // ← 先截断，旧数据已释放

if (allocationSize > 0 && (long)allocationSize > _fs.FreeBytes)
    return V(FsResult.Error(NtStatus.DiskFull)); // ← 后检查，返回失败但数据已没了
```

**影响**：磁盘接近满时，任何带 `allocationSize` 提示的覆盖写（资源管理器复制、很多安装器）会**静默摧毁原文件**并返回失败——调用方认为"覆盖没发生"，实际原数据已丢。这是数据丢失级缺陷。

**修复建议**：把容量检查移到 `SetLength(0)` 之前；检查通过后再截断。若希望与 NTFS 完全一致（覆盖总是先成功截断、写阶段才报满），则至少应去掉这个"半拉子"的提前失败，二选一，不能两头都不占。

### P0-3 `Move` 未防御"移动进自身子树"：树成环（大小写可绕过）【实测复现】

**位置**：`RamDrive.Core/FileSystem/RamFileSystem.cs:119-147`

**事实**：`Move("\a", "\a\b")` 时 `ResolvePath("\a\b")` 在树仍包含源节点时解析，`newParent` 是源节点的子孙；随后源节点从旧父节点摘除并挂到自己子孙下，`Parent/Children` 成环。`FileNode.Dispose` 递归会沿环无限递归（卸载时栈溢出风险），成环子树也无法被常规工具删除。

**实测记录**：
- 常规重命名（`Move-Item \a → \a\inner\newa`）被 **Win32 层**拦下（"目标路径是源文件的子目录"）——文件系统自身并未拦截，防线在文件系统之外。
- **大小写绕过**：目标写成仅大小写不同的 `\A\inner\newa` 后，Win32 检查失效、请求到达文件系统并**成功执行**：目录树变成 `a\inner\newa\inner\newa\…` 的无限自嵌套（实测遍历到 260 字符路径上限仍在延续）。
- 后果实测：该结构无法用 `Remove-Item -Recurse`/`rd` 直接清理（路径无限增长）；实测后必须先重命名断开环中一条边（`Move a\inner\newa → t4\x`）才能逐级删除。可推知：任何启用长路径的递归遍历/备份工具会无限循环；卸载时 `RamFileSystem.Dispose` 的递归将撞环。

**连带发现**：参考实现 `MemfsReferenceFs.MoveFile`（MemfsReferenceFs.cs:387-437）用扁平字典规避了结构损坏，但同样不拒绝该操作，**oracle 本身与 NTFS 语义不符**——差分测试在此场景下"两边一起错"，测不出来。

**修复建议**：`Move` 开头沿 `newParent` 的 `Parent` 链上溯，若命中 `sourceNode` 则返回失败（适配层映射为 `STATUS_INVALID_PARAMETER`）——不要依赖 Win32 层的大小写敏感前缀检查。在参考实现中同步该规则（两处有 LOCKSTEP 约定，参考 `security-owner-enforcement` 的做法），并补集成测试（含大小写变体）。

### ~~P0-4~~（降级）删除/替换与打开句柄的共存：实测未复现，保留为设计建议【实测未复现】

**位置**：`RamFileSystem.cs:96-114`（`Delete → node.Dispose()`）、`WinFspRamAdapter.cs:569-594`（`Cleanup(Delete)`）

**原静态判断**：`Cleanup(Delete)` 会立即 `Dispose` 节点（释放页与锁），若其他句柄仍打开同一节点，后续读会撞上已释放对象；参考实现 `MemfsReferenceFs` 有 `RefCount` 而生产实现没有。

**实测结果（三条路径均未复现，行为与 NTFS 一致）**：
1. 显式 `File.Delete`（另一读句柄以 `FILE_SHARE_DELETE` 保持打开）：删除成功、名字消失，通过存活句柄读取返回**原数据**（24 字节完整）——正确的 pending-delete 语义；对 pending-delete 名字做 stat 返回"拒绝访问"，与 NTFS 的 `STATUS_DELETE_PENDING` 表现一致。
2. delete-on-close 句柄关闭（另一读句柄保持打开）：读句柄仍能读到原数据。
3. `MoveFileEx` 替换**仍有打开句柄**的目标：返回错误 5（ACCESS_DENIED），与 NTFS 一致——替换未发生，存活句柄数据完好。

**结论**：WinFsp 内核层把 `Cleanup(Delete)` 门控在最后一个句柄关闭、并对带打开句柄的替换做了访问检查，生产实现因此"被动正确"。降级为**设计健壮性建议**而非确认缺陷：生产实现的正确性依赖对 WinFsp 门控行为的隐式假设（参考实现用 `RefCount` 显式建模了这一点）；若未来启用 `SupportsPosixUnlinkRename` 等改变删除时机的选项，无引用计数的立即 `Dispose` 就会暴露。建议仍按参考实现补引用计数，并把这三条用例固化成回归测试。

### P1-1 `Move` 允许"文件替换空目录"，与 NTFS 及自家 oracle 分歧【实测复现】

**位置**：`RamFileSystem.cs:129-134`

**事实**：`replace=true` 时仅当目标是**非空**目录才拒绝；空目录会被文件直接替换。NTFS 不允许用文件替换目录（空也不可以），`MemfsReferenceFs.MoveFile:399-400` 对**任何**目录目标返回 `STATUS_ACCESS_DENIED`。生产实现与差分 oracle 直接矛盾——差分腿没抓到只是因为现有测试没有构造"替换空目录"用例。

**实测记录**：`MoveFileEx(file, emptyDir, MOVEFILE_REPLACE_EXISTING)` 返回**成功**，目标目录变成一个文件；同样调用在 NTFS 上返回错误 5。一行即可复现。

**修复建议**：`existing.IsDirectory → return false`，适配层映射为 `NtStatus.AccessDenied`（与参考实现对齐）。

### P1-2 `SetFileSize(setAllocationSize=true)` 不截断逻辑大小

**位置**：`WinFspRamAdapter.cs:441-459`

**事实**：该分支只做容量闸门后原样返回，`newSize < FileSize` 时不截断。WinFsp 契约（及参考实现 `SetFileSizeInternal`，MemfsReferenceFs.cs:335-357 的 `if (n.FileSize > newSize) n.FileSize = newSize;`）要求分配大小缩小时同步截断文件大小。`Comparators.CompareFileInfo` 恰好比较 `FileSize`——一旦有测试走到这条路径，差分必炸；现在没炸只说明无覆盖。

**修复建议**：在 `setAllocationSize && newSize < node.Content.Length` 时先 `SetLength(newSize)`；同时考虑该分支是否应真正 `Reserve`（当前注释承认"不预留、写时分配"，这使复制在过半程时才报 DISK_FULL，与 `SetLength` 扩展分支的预留行为不对称）。

### P1-3 预留回收失败路径导致记账漂移（`_reservedCount` 可为负）

**位置**：`PagedFileContent.cs:149-160`

**事实**：阶段 2 先 `Unreserve` 自己的预留去换容量，`RentBatch` 失败后尝试恢复：

```csharp
if (unreservedForAlloc > 0)
{
    _pool.Reserve(unreservedForAlloc);              // ← 可能失败（容量已被别人拿走）
    Interlocked.Add(ref _reservedPages, unreservedForAlloc); // ← 无论成败都加回文件级计数
}
```

若 `Reserve` 失败而文件级 `_reservedPages` 照样加回，后续截断/删除会向池子 `Unreserve` 从未预留过的额度 → 池级 `_reservedCount` 变负 → `Reserve` 的容量检查被负数放宽 → 长期运行下超卖加剧。这是 P0-1 同源问题的次生伤口。

**修复建议**：与 P0-1 的 `committed` 统一计数一起重构；至少在 `Reserve` 失败时不加回 `_reservedPages`，并打一条警告日志（这是不变式被打破的信号，参考 `FallbackSdFor` 的一次性告警模式）。

### P1-4 `SetFileSecurity` 对畸形安全描述符无异常防护

**位置**：`WinFspRamAdapter.cs:485-521`

**事实**：`new RawSecurityDescriptor(modificationDescriptor, 0)` 遇到畸形/恶意构造的字节会抛 `ArgumentException` 等，异常直接穿透到 WinFsp 分发器。另外适配器未重写 `IFileSystem.ExceptionHandler`（只有 `DifferentialAdapter` 重写了），生产环境异常的可观测性依赖 EventLog 的兜底。

**修复建议**：`try` 包裹解析，失败返回 `STATUS_INVALID_SECURITY_DESCRIPTOR`；在 `WinFspRamAdapter` 中重写 `ExceptionHandler`：记录日志（含回调上下文）并返回保守的失败状态。SACL 写入无 `SeSecurityPrivilege` 校验属 WinFsp 无调用方令牌的系统性限制，代码注释已诚实说明——建议在 `docs/` 中单列一节风险接受声明。

### P1-5 `Cleanup(Delete)` 无视删除结果，无条件发送 `ActionRemoved` 通知

**位置**：`WinFspRamAdapter.cs:569-579`

**事实**：`_fs.Delete(fileName)` 的返回值被丢弃，随后总是 `Notify(...ActionRemoved...)`。若 `CanDelete` 与 `Cleanup` 之间有并发创建子项导致删除失败，内核缓存会收到"已删除"的失效通知——之后是反向的陈旧（文件在、缓存说不在）。概率低，但与"通知矩阵"的严谨风格不符。

**修复建议**：`if (_fs.Delete(fileName)) { Notify(...) }`。

### P2 健壮性与边界（择要）

1. **`AllocationSize` 稀疏上报可能小于 `FileSize`**（`WinFspRamAdapter.cs:694-707`，`MakeFileInfo` 用 `AllocatedBytes`）。`SetLength` 纯扩展后未写任何数据时上报 `AllocationSize=0 < FileSize`。稀疏文件在 NTFS 上合法，故标记为"判断"级风险而非断言缺陷，但内核 Cc 与部分应用假设 `Allocation ≥ Size`，建议观察 `EnableKernelCache=true` 下是否有应用异常，必要时对 `AllocationSize` 取 `max(allocated, roundup(FileSize))`。
2. **`SetFileAttributes(fileAttributes==0)` 不清属性**（`WinFspRamAdapter.cs:428`）：多了个 `&& fileAttributes != 0` 守卫，与参考实现（0 会覆盖）和 `SetBasicInfo` 语义分歧。同理 `OverwriteFile` 未像参考实现那样无条件 `| Archive`（`WinFspRamAdapter.cs:309-312`）。两处都是差分可测的语义漂移，建议对齐。
3. **目录枚举排序用 `OrdinalIgnoreCase`**（`RamFileSystem.cs:152-164`、`WinFspRamAdapter.cs:642`）：NTFS 枚举序是大写序（NLS upcase 表），与 `OrdinalIgnoreCase` 在非 ASCII 名上不保证一致；`marker` 分页在极端命名下可能重复/遗漏条目。建议至少记录该近似，或改用与 `MemfsFileNameComparer` 一致的比较器（它已经存在，顺手统一）。另外 `ListDirectory` 每次枚举在全局结构锁内做全量 `OrderBy`，大目录下单次枚举成本 O(n log n) 且阻塞所有结构操作，可缓存"脏标记排序结果"。
4. **文件名/路径零验证**：`FindNodeInternal`/`ResolvePath` 只做 `Split('\\')`。保留名（`CON`/`NUL`）、非法字符（含控制字符 `0x01-0x1F`）、超长名、空段（`\\a\\\\b` 被静默归一）、尾随点/空格均未校验。多数会被 WinFsp 内核拦下，但 `CreateInitialDirectories` 是**绕过 WinFsp 直接建树**的，配置里的怪名字会真实落地（`DirectoryNode.Validate` 的字符集也不含控制字符，`DirectoryNode.cs:14`）。建议在 `RamFileSystem.CreateFile/CreateDirectory` 内做统一校验并返回 `STATUS_OBJECT_NAME_INVALID`，`Validate()` 补控制字符检查。
5. **配置无防御**：`PageSizeKb=0` → `_pageSize=0` → 除零，启动即崩；`CapacityMb≤0` → 0 页，全盘 DISK_FULL 且无提示。建议在 `PagePool` 构造或 Options 校验（`IValidateOptions`）中显式报错。
6. **根 DACL 对 Everyone 全控且不可配置**（`WinFspRamAdapter.cs:55`，`FA;;;WD`）。作为缓存盘这是有意为之（对齐 memfs 默认），但 RAM 盘常被用来放临时敏感产物；建议把根 SDDL 提升为配置项，文档明示默认值的风险。
7. **`Unmounted` 未清空 `_host`**（`WinFspRamAdapter.cs:126-129`）：卸载后 `Notify` 仍可能对已停止的分发器发 IOCTL。低风险但一行修复。
8. **`EnsureMountMgrFromFSD` 硬编码 `WOW6432Node`**（`WinFspHostedService.cs:172-196`）：64 位进程读 32 位视图注册表的写法可行但脆；写失败静默忽略已有注释说明，可接受。

### P2 构建、发布与卫生

9. **版本号四处漂移**：发行包 0.4.7 ↔ `Directory.Build.props` 的 `1.0.0-dev` ↔ `RamDrive.iss` 的 `0.0.0-dev` ↔ Setup.bat 下载的 WinFsp **2.1.25079** ↔ CI/iss/release.yml 使用的 **2.1.25156**。CI 会覆盖版本，问题不大，但 Setup.bat 用户会拿到旧一个版本的 WinFsp，建议统一到单一版本源（如 `Directory.Build.props` + 一处 WinFsp 版本常量）。

### P3 风格与长期维护（摘要）

- `FileNode` 可变性过宽：`Name/Attributes/时间戳` 全是 public setter、`Children` 字典直接外露；收敛为内部可见可显著降低未来误用（P0-3 这类 bug 的温床）。
- `RamFileSystem.cs:37` 注释仍写 "Dokan convention"、README 写 `NativeMemory.AllocZeroed` 实际为 `AlignedAlloc`——过时文字。
- `OWNER_SECURITY_INFORMATION`/`STATUS_INVALID_OWNER`/`IsRejectedOwnerChange` 在生产与参考两处复制（有 LOCKSTEP 注释约束）；可提取到共享常量类并加"两处必须一致"的单元测试，替代纯注释约定。
- `Notify` 每次装箱一个五元组进线程池——仅在 `EnableNotifications=true`（调试开关）时发生，可接受，但若转正为生产特性需去装箱。
- `PagePool.AllocateNewPageIfUnderCapacity` 并发下最多每竞争者多分配 1 页（`allocated` 瞬时越过 `maxPages` 少许）；`AllocateNativePage` OOM 抛出时 `_allocatedCount` 已递增不回滚。均为低频小漂移，随 P0-1 的 `committed` 重构一并解决为佳。

## 四、分维度诊断摘要

**正确性**：主路径（读写/缓存一致性/安全描述符继承/文件 ID）被真实世界 bug 反复打磨，注释中保留了完整的因果链，这部分质量很高。失分全部集中在结构操作（Move/Delete/Overwrite）的失败路径与生命周期管理——恰好是差分测试与混沌测试当前没覆盖的角落（见 §六）。

**并发**：三阶段写协议（读锁扫描 → 锁外批量租页 → 写锁内装填+memcpy）是正确的性能导向设计，`ReaderWriterLockSlim` 分级与 CAS 预留的思路清晰。核心暗角是**预留记账没有与空闲栈弹页纳入同一原子域**（P0-1/P1-3）——这是"多个计数器分别原子、组合不变式无人守护"的经典模式，TLA+ 模型应当扩展覆盖。

**安全**：页归还清零（防跨文件数据泄漏）+ 截断尾部清零做得规范；SD 继承"非空不变式 + 防御回退 + 每路径一次性告警"是很好的工程实践。弱点：根 DACL 过宽且硬编码、SACL 无特权校验（平台限制）、畸形 SD 无防护（P1-4）。

**性能**：设计目标（热路径零托管分配、同步 ValueTask、稀疏页、批量租还）与实测基准自洽；`FsTracer` 用 `[Conditional]` 实现生产零开销是教科书式处理。可优化点（大目录枚举排序、全局结构锁争用）属可扩展性话题，当前规模不紧迫。

**可维护性**：本库最强维度。每个历史缺陷有 spec（openspec/）+ 复盘（docs/）+ 回归测试 + 规范引用四件套；代码注释解释"为什么"而非"是什么"。扣分项是无分析器/无 editorconfig 的"裸奔"静态检查环境。
